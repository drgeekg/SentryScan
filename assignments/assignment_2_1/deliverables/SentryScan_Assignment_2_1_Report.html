1. Executive Summary & Theoretical Context

Assignment 2.1 advances SentryScan from a static single-threaded reflex scanner to an asynchronous, concurrent monitoring agent situated in a dynamic environment (Russell & Norvig, Ch. 2).

1.1 Concurrency in Situated Agents

In dynamic real-world environments, percepts arrive asynchronously while the agent is deliberating. A background thread model decouples sensing from acting: - Producer-Consumer Telemetry Pipeline: A non-blocking background daemon (MonitorDaemon) continuously polls synthetic endpoints and enqueues telemetry into a thread-safe synchronized buffer (queue.Queue). - Mutual Exclusion & State Integrity: Multi-threaded telemetry updates risk catastrophic lost updates without synchronization primitives. We formally demonstrate race conditions and verify thread safety via explicit mutex locks.

1.2 Defensive Integrity Sensing & Ground-Truth Isolation

Autonomous agents operating in untrusted environments must detect sensor tampering (poisoning) without access to oracle labels: - Plausibility Checking: Evaluates temporal freshness, cryptographic duplicate digests, port-banner contradictions, and prompt-injection strings. - Isolated Evaluator Sidecar: Ground-truth mutation labels are stored exclusively in an isolated sidecar, ensuring agent decisions are strictly unassisted.

2.1 Lost Updates Race Condition Experiment (src/sentryscan/concurrency/stats.py)

To prove the necessity of concurrency synchronization, 10 concurrent threads each perform 10,000 increments on a shared counter: - Without Mutex Lock: Substantial race conditions cause 440+ lost updates (actual count: 99,560 vs expected 100,000). - With Mutex Lock (threading.Lock): 100% thread safety achieved: exactly 100,000 / 100,000 updates preserved with zero lost counts.
